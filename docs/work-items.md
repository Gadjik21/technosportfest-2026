# Рабочие задачи по участникам

Каркас репозитория уже содержит FastAPI, JWT/Origin, первую миграцию пользователей, пустые роутеры модулей, React/Vite и генерацию типов. Задачи ниже описывают оставшуюся предметную реализацию и доработку каркаса.

## Бэкендер 1 — Identity и Competitions

**v1:** Использовать готовый FastAPI/Alembic/PostgreSQL каркас, JWT/Origin и `/auth/*`; дополнить сид дисциплинами, реализовать `/disciplines`, создание/публикацию/чтение соревнований, заявку и список участников. Реализовать `CompetitionPort`, чтобы Б2 мог публиковать результат в общей транзакции. Ограничения дат, повторной заявки и доступа обязательны.

**v2:** `/me`, `PATCH /me`, `/me/registrations`, `PATCH /competitions/{id}`. Уточнить миграции и договориться с Б2 об одном Alembic head.

**v3:** Запуск с чистой БД, сид демоданных без настоящих персональных данных, проверка прав спортсмена против организаторских маршрутов, README запуска.

## Бэкендер 2 — Results, Rating и Content

**v1:** `PUT` черновика, список черновиков, атомарная публикация, публичные результаты и `/ratings`. Брать регистрацию через `CompetitionPort`, спортсменов пачкой через `IdentityPort`. Рейтинг рассчитывать из опубликованных результатов.

**v2:** `/me/results`, `/me/rating`, новости и документы с публичными HTTPS-ссылками. Никакой загрузки файлов в MVP.

**v3:** Проверить, что черновик не влияет на рейтинг, публикация идемпотентна по эффекту (повторный запрос `409` без новых баллов), публикация и `completed` откатываются вместе при ошибке.

## Фронтенд — владелец запроса

**v1:** сгенерировать типы из OpenAPI; сделать API-клиент с cookie; экраны входа, каталога, карточки, заявки, участников, редактора результатов и рейтинга. Пока API нет, использовать JSON-примеры той же формы.

**v2:** профиль и кабинет спортсмена, новости/документы, адаптивность. Для `401` показывать вход, для `403` запрет доступа, для `409` предметное сообщение, для `422` ошибки полей.

**v3:** пройти сценарий на реальном API с чистой БД и сидом; убедиться, что публикация сразу обновляет результат и рейтинг без перезагрузки страницы.

## Продакт / дизайн

**v1:** макеты сквозного пути спортсмена и организатора, включая загрузку, пустые списки, закрытую регистрацию, повторную заявку, ошибку входа и подтверждение публикации.

**v2:** профиль, история результатов, рейтинг с видимой формулой, новости и документы, мобильный вид.

**v3:** демонстрационный сценарий и приёмка: эксперт без подсказок входит спортсменом, подаёт заявку, входит организатором, публикует результат, видит изменение рейтинга.

## Единый критерий PR

Изменение API включает поправку `contracts/openapi.json` и соответствующего JSON-примера. Для работы с БД — миграцию. Для изменения правил рейтинга или статусов — обновление `docs/architecture.md`. Прежде чем менять общий контракт, владелец PR уведомляет фронтенд и второго бэкендера.

## Минимум автотестов

Пишем тесты вместе с рискованной логикой, а не отдельным этапом перед сдачей. Процент покрытия не устанавливаем; проверяем поведение через API и реальную БД там, где важны транзакции.

| Владелец | Проверки для своего PR |
|---|---|
| Б1 | Спортсмен не получает роль организатора; повторная заявка не создаёт дубль; после дедлайна заявка закрыта; спортсмен не вызывает организаторские методы. Три проверки auth уже есть в `backend/tests/test_auth.py`. |
| Б2 | Черновик не виден публично и не влияет на рейтинг; публикация меняет статус соревнования и результаты одной транзакцией; повторная публикация не начисляет баллы; формула рейтинга и ничьи работают. Публикацию и откат проверять на PostgreSQL: SQLite не проверяет блокировки строк как PostgreSQL. |
| Фронтенд + оба бэкендера | К MVP один автоматизированный сквозной тест в браузере на собранной системе: вход спортсмена → заявка → вход организатора → публикация → результат и обновлённый рейтинг. Продакт/дизайн отдельно проходит этот путь вручную как эксперт. |

Полный набор тестов для каждого декоративного состояния и требование 100% покрытия сейчас не нужны. Перед слиянием PR должны проходить существующие тесты, сборка фронтенда и проверка OpenAPI-контракта.
