## 3. Кейс №2 — что требуется (сжато)

Обязательный сквозной сценарий защиты:
**организатор создаёт контест → добавляет задания → публикует → спортсмен открывает → отправляет решение → организатор проверяет → появляются результаты → результат сохраняется в профиле спортсмена (и в рейтинге, если он есть).**

Семь вещей, которые обязаны работать к концу дня (дословно из `kase_2.docx`):
1. Создание соревнования (с заданиями) организатором
2. Добавление заданий (минимум 3 для демо: название, условие, макс. балл)
3. Страница соревнования для спортсмена (всё в одном месте: описание, статус, задания, отправка, результат)
4. Отправка хотя бы одного решения (текст / файл / ссылка — команда выбирает один способ)
5. Проверка решения организатором (ручная, выставление баллов)
6. Итоговая таблица (место, ФИО, баллы; правило дележа мест при равенстве)
7. Появление результата в профиле спортсмена **и в истории/рейтинге**, если рейтинг уже есть

Явно не требуется (не тратить на это время): свой компилятор/online judge, изолированный запуск кода, командные заявки, промышленная инфраструктура — см. полный список в `kase_1.docx`/`kase_2.docx`.

## 4. Технический план (минимальный риск для существующего кода)

Ключевая идея: **не трогать существующие таблицы/контракты `results`**, а досчитывать финальный балл контеста и публиковать его через уже готовый механизм результатов и рейтинга (`upsert_draft` → `publish_results` в `results/service.py`). Так рейтинг и профиль спортсмена начинают показывать результат контеста бесплатно, без единой строчки новой логики в Results/Rating — ровно то, что просит п. 7 кейса №2 («связь с платформой первого этапа»).

Соревнование становится «контестом», если у него есть задания — отдельного поля/типа заводить не нужно.

### Новый модуль `backend/app/modules/contests/`

- **Модели** (новая миграция `0005_contests.py`, `down_revision = "0004_competitions"`):
  - `tasks`: `id, competition_id, title, statement, max_score, order_index, created_at`
  - `submissions`: `id, task_id, registration_id, kind (text|link), content, submitted_at, score (nullable), graded_at`
  - Ограничения: `unique(task_id, registration_id)` — одно (актуальное) решение на задание, повторная отправка перезаписывает (проще для MVP, чем история попыток).
- **Ports** (по аналогии с `competitions/ports.py`): `ContestsPort.get_registration(...)`, переиспользовать `CompetitionPort` из `competitions` для проверки регистрации/принадлежности, не импортируя чужие ORM-модели.
- **Роуты**:
  - Организатор: `POST/GET/PATCH/DELETE /competitions/{id}/tasks`
  - Организатор: `GET /competitions/{id}/submissions` (очередь на проверку), `PATCH /submissions/{id}` (score)
  - Спортсмен: `GET /competitions/{id}/tasks` (видно после публикации), `PUT /competitions/{id}/tasks/{taskId}/submission`, `GET /competitions/{id}/my-submissions`
  - Организатор: `POST /competitions/{id}/contest/finish` — считает сумму баллов по каждой заявке из `submissions.score`, вызывает существующий `upsert_draft` для каждой заявки, затем существующий `publish_results` (место — по убыванию суммы, дележ мест — уже реализованное правило из Results). Это одна новая функция-оркестратор, а не новая бизнес-логика подсчёта рейтинга.
- **Статус «Идёт»**: не добавлять новый статус в `competitions.status` (не трогать таблицу и контракт Б1/Б2) — вычислять на фронте/в ответе как `published && now between startsAt и endsAt`. Черновик/Опубликован/Завершён остаются как есть.

### Фронтенд

- `OrganizerPages.tsx`: в `ManageCompetition` добавить вкладку «Задания» (список + форма создания/редактирования) и вкладку «Проверка решений» (очередь, поле для балла, кнопка «Завершить контест и опубликовать результаты» — по сути такой же `ConfirmDialog`, как уже есть для публикации результатов).
- `PublicPages.tsx` / `CompetitionDetail`: если у соревнования есть задания — показывать список заданий и, для авторизованного участника, форму отправки решения (текст или ссылка) прямо на той же странице (кейс №2 явно просит не размазывать по разделам).
- Статусы решения на UI: «Не отправлено» / «Отправлено, ждёт проверки» / «Оценено: N из M баллов» — это и есть недостающие «состояния» из дизайна.

### Контракт

Обновить `contracts/openapi.json` и `contracts/examples/` под новые эндпоинты — обязательное правило репозитория (см. `README.md`, «Кто меняет что»). Делает тот, кто пишет бэкенд-часть, до того как фронтенд начнёт верстать.

## 5. Задачи по ролям

### Бэкенд — модуль Contests (новый, отдельные файлы → минимум конфликтов с Б1/Б2)
**Сначала (маст-хэв):** миграция `tasks`+`submissions`; CRUD заданий организатором; отправка/перезапись решения спортсменом; список решений на проверку и простановка балла; `POST .../contest/finish` с агрегацией через существующие `upsert_draft`/`publish_results`.
**Потом:** валидации (нельзя отправлять решение до старта или после `endsAt`; нельзя менять задания после публикации соревнования; нельзя завершить контест, если есть неоценённые решения — или явно разрешить с предупреждением).
**Демо-данные:** в `app/seed.py` добавить `--contest-demo`: тестовый контест «Тестовый контест по алгоритмическому программированию» с 3 заданиями, несколькими участниками, отправленными решениями и выставленными баллами.

### Фронтенд
**Сначала:** вкладка «Задания» + форма в `ManageCompetition`; блок заданий и форма отправки на `CompetitionDetail`; вкладка «Проверка решений» с простановкой баллов и кнопкой завершения контеста.
**Потом:** статусные бейджи решения, отображение времени до конца (не обязательно таймер — достаточно текста «до конца: HH:MM»), обновление типов через `npm run types:api` после правки контракта.

### Дизайн (нужно параллельно и быстро, блокирует фронтенд)
Дорисовать по факту недостающие состояния экранов, которые уже есть в структуре флоу, но без деталей:
1. **«Задачи соревнования (спортсмен)»**: список заданий с баллами, состояние «не отправлено» / «на проверке» / «оценено», форма отправки (текст или ссылка — выбрать один способ и зафиксировать это в макете, чтобы фронтенд не гадал).
2. **«Организатор: задачи соревнования»**: список/форма создания задания; отдельно — очередь решений на проверку с полем ввода баллов и кнопкой «Завершить контест».
3. **Итоговая таблица результатов контеста**: место / ФИО / сумма баллов, желательно с раскрытием баллов по каждому заданию.
4. Пустые состояния: «заданий пока нет», «решений на проверку нет».
Дизайн «Сотрудники и права» — не делать, не входит в обязательный скоуп ни одного кейса.

## 8. Демо-сценарий для защиты (подготовить заранее, не показывать вживую в моменте)

1. Организатор входит → создаёт контест «Тестовый контест по алгоритмическому программированию» → добавляет 3 задания → публикует.
2. Спортсмен входит → открывает контест → отправляет решение по одному из заданий.
3. Организатор видит решение в очереди → выставляет баллы → так по всем участникам.
4. Организатор жмёт «Завершить контест и опубликовать результаты».
5. Итоговая таблица появляется на странице соревнования; результат и обновлённые баллы видны в профиле и рейтинге спортсмена без перезагрузки логики (это бесплатно приходит из существующего Results/Rating).

Подготовить эти демоданные заранее через `seed.py`, чтобы не полагаться на ручной ввод во время защиты (до 7 минут на показ + 3 минуты на вопросы — по регламенту `kase_2.docx`).
